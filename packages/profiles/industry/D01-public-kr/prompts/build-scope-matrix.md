# 과업대비표 작성

## 역할
공공 정보화사업 감리 대응 실무자다. RFP 요구사항이 어느 산출물로 이행됐는지
대응표를 작성한다.

## 요구사항추적표와 혼동하지 말 것

| | 요구사항추적표 (AN-03) | 과업대비표 (AU-01) |
|---|---|---|
| 목적 | 내부 추적 | 계약 이행 증명 |
| 축 | 요구사항 → 설계 → 시험 | RFP 요구사항 → 산출물 |
| 독자 | 개발팀 | 감리원, 발주기관 |
| 질문 | "이 요구가 어디서 구현되고 검증됐나" | "발주한 과업이 전부 이행됐나" |

둘을 하나로 합치면 감리에서 과업 누락 소명이 불가능해진다.
과업대비표는 **RFP에 적힌 요구사항 하나도 빠짐없이** 행으로 들어가야 한다.

## 입력
- `{{rfp_requirements}}` — RFP 또는 요구사항정의서의 요구사항 목록.
  사용자가 제공한다. 코드에서 도출하지 않는다.
- `{{generated_requirements}}` — 코드에서 복원한 요구사항 (증거 앵커 보유)
- `{{artifacts}}` — 생성된 산출물 목록
- `{{change_requests}}` — 과업변경 요청·승인 내역 (있는 경우)

## 절대 규칙

1. **RFP 요구사항을 창작하지 않는다.** `{{rfp_requirements}}`가 비어 있으면
   과업대비표를 만들 수 없다. 코드에서 복원한 요구사항은 RFP 요구사항이
   아니다. 그것은 "구현된 것"이지 "발주된 것"이 아니다.

2. **이행 여부를 단정하지 않는다.** 코드 증거로 확인할 수 있는 것은
   "대응되는 구현이 존재한다"까지다. "과업을 완수했다"는 발주기관의 판단이다.
   `status`는 다음 넷 중 하나로만 기재한다.

   | 값 | 의미 |
   |---|---|
   | `대응_확인` | RFP 요구사항에 대응하는 구현과 산출물이 모두 확인됨 |
   | `부분_대응` | 대응 구현은 있으나 산출물이 불완전하거나 범위가 좁음 |
   | `대응_없음` | 코드와 산출물에서 대응을 찾지 못함 |
   | `확인_불가` | 코드로 판정할 수 없는 요구(교육, 인력, 일정 등) |

3. **`대응_없음`을 숨기지 않는다.** 이것이 과업대비표의 존재 이유다.
   누락을 드러내야 착수 단계에서 잡을 수 있다. 감리에서 발견되면 늦다.

4. **PMR·PSR 계열은 대부분 `확인_불가`다.** 프로젝트관리요구사항과
   프로젝트지원요구사항은 인력 투입, 교육, 보고 주기 같은 것이라
   소스코드에 흔적이 없다. 억지로 대응시키지 않는다.

## 출력 스키마

```json
{
  "scope_matrix": [
    {
      "rfp_req_id": "SFR-001",
      "rfp_req_name": "민원 신청 기능",
      "rfp_req_text": "RFP 원문 (요약하지 말고 그대로)",
      "status": "대응_확인",
      "mapped_requirements": ["SFR-001"],
      "mapped_artifacts": ["DE-03", "DE-11", "IM-01"],
      "evidence": [
        {
          "repo_path": "src/civil/application.py",
          "start_line": 20,
          "end_line": 95,
          "symbol_fqn": "civil.application.ApplicationService.submit"
        }
      ],
      "gap_note": null,
      "change_request_refs": []
    },
    {
      "rfp_req_id": "PMR-003",
      "rfp_req_name": "주간 진척보고",
      "status": "확인_불가",
      "mapped_requirements": [],
      "mapped_artifacts": [],
      "evidence": [],
      "gap_note": "프로젝트관리 요구사항으로 소스코드에 대응물이 존재하지 않는다. 회의록·보고서로 별도 증빙해야 한다."
    }
  ],
  "summary": {
    "total": 0,
    "대응_확인": 0,
    "부분_대응": 0,
    "대응_없음": 0,
    "확인_불가": 0
  },
  "unmapped_implementations": [
    {
      "requirement_id": "SFR-020",
      "note": "코드에는 있으나 RFP 요구사항과 대응되지 않는다. 과업 범위 외 구현이거나 과업변경 누락일 수 있다."
    }
  ]
}
```

## `unmapped_implementations`가 중요한 이유

RFP에 없는데 구현된 기능은 두 가지 중 하나다.

- **과업 범위 외 구현** — 사업자가 무상으로 추가한 것. 검수 대상이 아니다
- **과업변경 누락** — 변경은 합의했는데 과업변경요청서를 안 쓴 것. 감리 지적 대상

어느 쪽인지는 도구가 판정하지 않는다. 목록만 제시하고 사용자가 분류한다.

## 하지 말 것

- RFP 원문 요약·의역 (원문 그대로 옮긴다. 감리원이 대조한다)
- `대응_없음` 항목의 누락이나 `부분_대응`으로의 완화
- 코드 증거 없는 `대응_확인` 판정
- PMR·PSR을 억지로 코드에 대응시키기
